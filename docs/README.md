# docs/ — 판단의 근거를 남기는 곳

README에 두면 본문이 묻히지만 지우기는 아까운 기록들을 모았다.

각 폴더의 README는 **"이 코드가 무엇을 하고 왜 그렇게 설계했는가"**만 담는다.
그 과정에서 겪은 시행착오, 폐기된 방법, 검증 수치는 여기로 뺐다.

## data/ 와 무엇이 다른가

CSV가 양쪽에 다 있어서 헷갈리기 쉬운데, 기준은 파일 형식이 아니라 **누가 읽는가**다.

| | `data/` | `docs/` |
|---|---|---|
| 성격 | 파이프라인이 **읽고 쓰는** 것 | 사람이 **근거로 읽는** 것 |
| 예 | 실거래가 원본, 표면주거비 산출물 | 배정 정확도 검증표, 재선택 진단표 |
| 지우면 | 코드가 안 돈다 | 코드는 돌지만 **왜 그렇게 판단했는지 알 수 없다** |

여기 있는 CSV는 전부 **스크립트가 만들어낸 검증 결과**다. 파이프라인의 입력이
아니라 출력이고, 다시 만들 수는 있지만 **그 시점의 판단을 증명하는 자료**라
문서 옆에 둔다.

## 근거 자료 (스크립트 출력)

| 파일 | 만든 스크립트 | 무엇을 증명하나 |
|---|---|---|
| `행정동_신뢰도.csv` | `build_dong_reliability.py` | 427개 동의 신뢰도 등급. `dim_dong_reliability.sql` 의 원천 |
| `도로명근사_정확도_동별.csv` | `verify_road_accuracy.py` | 도로명 배정 정확도를 정답 5,821건으로 역산한 결과 |
| `표면주거비_배정방식_동별.csv` | `aggregate_assign_method.py` | 동별로 어떤 방식(지번/도로명/텍스트)으로 배정됐는지 |
| `표면주거비_배정방식_동별_보정.csv` | 〃 | 위 파일의 보정본 |
| `fallback_후보_법정동기반.csv` | `extract_adjacent_by_bjd.py` | 법정동 공유로 뽑은 인근 후보 24행 초안 |
| `재선택_결과.csv` | `reselect_routes.py` | 대표 경로를 다시 고른 뒤의 변동 진단 |

**이 파일들은 수기로 편집하지 않는다.** 값이 이상하면 만든 스크립트를 고쳐
다시 돌린다. `행정동_신뢰도.csv` 는 특히 그렇다 — 임계값을 바꾸려면
`build_dong_reliability.py` 상단 `TH_` 상수를 고쳐야 하고, 여기서 손대면
`dim_dong_reliability.sql` 과 어긋난다.

## 예외 하나

`verify_config.json` 은 이 폴더에서 **유일하게 코드가 읽는 파일**이다.

`verify_road_accuracy.py` 가 템플릿을 생성하고, 사람이 컬럼명을 직접 적어 넣은
뒤 `--run` 이 그것을 읽어 검증을 실행한다. 성격상 설정 파일이지만, **검증
실행 조건도 근거의 일부**라 결과 옆에 두었다.

```
python src/analysis/verify_road_accuracy.py         # 템플릿 생성 + 구조 덤프
# docs/verify_config.json 에 컬럼명 작성
python src/analysis/verify_road_accuracy.py --run   # 검증 실행
```

## 왜 지우지 않고 남기는가

**결론만 적으면 다음 사람이 같은 함정에 빠진다.**

이 프로젝트에서 같은 종류의 버그가 여덟 번에 걸쳐 다른 얼굴로 나타났다.
"제" 표기 → 전국 단위 목록 → 인코딩 손상 → 가운뎃점. 매번 "이제 다 고쳤다"고
판단했지만 아니었다.

폐기한 군집 모델도 마찬가지다. 지우면 "처음부터 k=6이었다"가 되어, 왜 그
방식을 택했는지 설명할 수 없어진다.

검증 CSV 도 같은 이유로 남긴다. `dim_dong_reliability` 에 "마장동은
unreliable" 이라고만 적혀 있으면 그 판정을 믿을 근거가 없다.
`도로명근사_정확도_동별.csv` 에 검증 거래 수와 정확도가 있어야
**"66건 중 정확도 0%, 전부 이웃 동으로 잡힘"**을 보일 수 있다.

> 코드는 다시 짤 수 있지만 **왜 그렇게 했는지는 기록하지 않으면 사라진다.**
