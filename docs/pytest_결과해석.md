# pytest 결과 해석

3단계 pytest 도입(2026-09-07) 기록. 테스트 자체의 사용법은 `tests/README.md` 참고.

## 요약

테스트 249건. 도입 과정에서 실제 버그 7건을 찾았고 모두 고쳤다.
**7건 모두 화면상으로는 정상으로 보이던 것들이다.**
크래시로 드러난 것은 1건뿐이고, 나머지는 값이나 표시만 조용히 틀렸다.

## 방어 세 겹

산식이 다시 갈라지려면 셋을 전부 뚫어야 한다. 한 겹만으로는 각각 사각지대가 있다.

| 겹 | 보는 것 | 못 보는 것 |
|---|---|---|
| 소스 | 상수 참조, 조용한 기본값, 파라미터 이중정의, 호출부 인자 누락, 미정의 이름 | 실제 계산 결과 |
| 배선 | app.py 가 네 페이지에 같은 인자를 넘기는가 | 넘긴 뒤 무시하는 경우 |
| 값 | 총부담 일치 + 입력 변경 시 반응 | 코드 구조상의 위험 |

값 검사만 있으면 "네 페이지가 다 같이 무시하는" 경우를 놓친다.
age 누락(아래 3번)이 정확히 그랬다. 나이를 전부 무시했으므로 값은 일치했다.

## 찾은 버그

### 1. `list_work_options` 미import (web/app.py)

`api_suggest()` 가 import 하지 않은 이름을 호출했다. `NameError` 가 나지만
그 줄이 `try/except Exception` 안이라 경고 로그만 남기고 전체 동 목록으로 폴백했다.

근무지 자동완성을 "그 거주지에서 갈 수 있는 곳"으로 제한하는 기능이
한 번도 동작한 적이 없었다. 경로는 거주동별 누적 80% 목적지만 수집했으므로
전체를 열어두면 사용자가 없는 조합을 골라 3페이지가 실패한다.

### 2. `qs` 미정의 (web/service.py, build_page5)

주거비 산출이 안 된 동을 골랐을 때 인근 행정동을 보여주는 분기에서
`qs` 를 정의하지 않고 썼다. `_fill_recommend` 에서 복사해 오면서
`qs = data.get("carry_qs") or ""` 한 줄만 안 따라왔다.

인근 행정동 카드가 뜬 적이 없고, 대신 "데이터베이스에 연결하지 못했습니다"가
표시됐다. DB 는 멀쩡한데 DB 장애로 보이는 상태였다.

### 3. `age` 전파 누락 (web/service.py)

3페이지가 다음 페이지로 가는 링크(`carry_qs`)를 만들 때 `age` 를 빼먹었다.
`app.py` 는 나이를 제대로 읽어 3페이지에 넘겼지만, 그 뒤로는 URL 에 없어서
4·5·6페이지가 `age=None` 으로 받았다.

`_pass_for_age(None)` 은 청년 기준을 쓰도록 설계돼 있어 크래시가 나지 않는다.
그래서 만 40세 이상에서만 드러났고, 시연 페르소나가 29세라 시연에서도 안 보였다.

실측: 만 45세 · 역삼1동 → 삼성역 · 21일 기준
3페이지 103.8만 / 4·5·6페이지 103.1만 (정기권 상한 62,000 vs 55,000 차이)

**막으려던 사고가 이미 다른 형태로 살아 있었다.** 어제는 산식이 세 벌이라
갈렸고, 이번엔 산식은 하나인데 입력이 도중에 샜다. 결말은 같다.

### 4. `extra` None 연산 (web/service.py, build_page5)

```python
extra = (tb.get("fare", 0) + ...)   # 키가 "없을 때"만 0. 값이 None 이면 None
```

`.get(키, 0)` 은 키가 없을 때만 기본값을 준다. 키가 있고 값이 `None` 이면
`None` 을 그대로 돌려줘 `None + 0` 에서 터진다.
바로 윗줄 `t_from` 은 `or 0` 으로 제대로 막고 있었다. 한 줄 차이로 방어가 달랐다.

근무지와 같은 동을 후보로 넣으면(직주일치) 통근 자료가 없어 `fare` 가 `None` 이 된다.
"직장 있는 동네로 이사하면?" 은 대안 탐색에서 가장 자연스러운 조회인데
5페이지가 크래시했다. 7건 중 유일하게 크래시로 드러난 건이다.

### 5. `_support_rank` 권역 누락 (web/service.py)

**산식을 한 곳에 모아도 인자를 빼먹으면 같은 사고가 난다는 사례.**

전월세전환율은 2026-09-06 에 단일 3.48% 에서 권역별 중앙값으로 바꾸고
헬퍼 하나(`_deposit_monthly`)로 통합했다. 그런데 호출부 다섯 곳 중
`_support_rank` 만 조회 결과를 안 넘기고 있었다.

```python
dep_monthly = _deposit_monthly(deposit)[0]   # 권역을 모르니 항상 5.9%
```

두 번째 인자가 없으면 조용히 전체 중앙값으로 물러서므로 크래시가 안 난다.
결과적으로 **화면에는 권역별 전환율로 계산한 월환산액이 뜨는데
정책 추천 순위는 전체 중앙값 5.9% 로 판단**하고 있었다.

동남권(5.39%) · 보증금 1억이면 월 42,500원 차이다. 월세가 그 사이 금액이면
화면은 "월세가 더 크다", 순위는 "보증금이 더 크다"가 된다.
서남권은 전체 중앙값과 값이 같아 그 권역만 보면 차이도 안 났다.

`_col_of` 가 `region_group` 을 내보내지 않아 전달이 끊겨 있었다.
`_col_of` 반환에 권역을 추가하고 `_support_rank` 가 넘기도록 고쳤다.

값 비교로는 절대 못 잡는 종류라, 이후 호출부 전수를 AST 로 검사한다
(`test_every_call_passes_region`).

### 6. `_MODE_KO` 키 순서 (web/service.py)

부분일치로 수단명을 찾는데 `"BUS"` 가 `"EXPRESSBUS"` 보다 앞에 있었다.
`"BUS" in "EXPRESSBUS"` 가 먼저 참이 되어 고속버스가 '버스'로 표시됐다.
표에 `"EXPRESSBUS": "고속버스"` 항목이 있는데 그 값이 나올 길이 없었다.

바로 아래 `_LINE_COLOR` 는 `"수인분당"` 을 `"분당"` 보다 앞에 두어
같은 함정을 피하고 있었다. 같은 파일에서 한쪽만 틀렸다.

서울 시내 통근에 고속버스가 낄 일이 거의 없어 영향은 작지만,
표 순서 자체를 검사하는 테스트를 넣어 항목이 추가돼도 잡히게 했다.

### 7. `nearest_routed_work` 가 거주동 자신을 돌려줌 (src/db/query_dong.py)

요청한 근무동으로 가는 경로가 없을 때 인근 근무동을 찾아주는 함수인데,
후보에서 거주동 자신을 빼지 않았다.

```sql
WHERE cr.home_code8 = %s AND cr.oneway_min IS NOT NULL   -- 자기 제외 없음
```

`fact_commute_route` 에는 내부통근 행(`home_code8 = work_code8`,
`route_type='내부통근_원본OD'`)이 있고 `oneway_min` 도 채워져 있어
조건을 통과한다. 그 결과 역삼1동 거주자에게 **"○○동 대신 역삼1동 기준으로
보여드려요"** 라고 안내하며 자기 동네로 출근하는 값을 보여줬다.

`list_work_options` 는 같은 목적의 함수인데 `work_code8 <> home_code8` 조건이
이미 있었다. 짝이 되는 두 함수의 조건이 한 줄 달랐다.

## 함께 정리한 것

- **`web/app.py` import 경로 단일화** — `from service import` 였다. `python web/app.py`
  로 실행하면 `sys.path` 에 `web/` 만 들어가 동작하지만, 루트가 함께 경로에 있으면
  같은 파일이 `service` 와 `web.service` **두 모듈로 이중 로드**된다. 그러면 한쪽을
  monkeypatch 해도 다른 쪽은 그대로여서 테스트가 거짓 통과한다.
- **`dim_time_value.source_note` 연도 오기** — 10,320원은 2026년 최저임금이다
  (2025년은 10,030원). 값은 맞고 라벨이 틀렸다. 방법론 문서·발표 자료에
  같은 문구가 옮겨졌는지 확인 필요.
- **`nearest_routed_work` 주석 오기** — "2순위 같은 권역"이라고 적혀 있었으나
  쿼리에 권역 조건이 없다. 실제로는 "그 외 자치구, 이동량 많은 순"이다.
- **BOM 4개 파일** — 파이썬 import 는 BOM 을 걷어내므로 앱은 정상 동작하지만
  `ast.parse` 등 소스를 읽는 도구는 멈춘다.

## 화면 판단 (2026-09-07 결정)

테스트가 드러냈지만 코드 버그는 아니었던 것들. 무엇을 보여줄지 정해야 했다.

### 미확인 조건을 화면에 밝힌다 — 배지 추가

2페이지 폼에 소득 칸이 없어 `_support_items` 는 `income=None` 으로 조회한다.
`_judge_policy` 는 이를 올바르게 처리해 `unchecked=["소득"]` 을 남기지만,
`_support_items` 가 라벨·아이콘·링크만 만들고 그 표시를 버리고 있었다.
결과적으로 월소득 128만원 이하 대상 정책이 월 280만원 버는 사용자에게
아무 표시 없이 떴다. **조회 계층은 옳고 표시 계층에서 끊긴 형태**였다.

소득 입력칸을 추가하는 대신 **배지로 밝히기로 했다.** 입력이 늘면 사용자가
피곤해지고, 이 화면의 목적은 자격 판정이 아니라 탐색 우선순위이기 때문이다.

`_support_items` 가 `unchecked` 를 `note` 로 실어 보내고 page6 이 알약 배지로
그린다. 경고가 아니라 안내이므로 색은 죽였다. 빨갛게 하면 "받을 수 없다"로 읽힌다.

소득 제한이 없는 정책(모두의카드·전세보증금반환보증)에는 배지가 안 붙는다.
아무 데나 붙으면 사용자가 무시하게 된다.

`unchecked` 를 그대로 문구로 만들므로, 나중에 소득 칸을 추가하면 배지가
자동으로 사라진다.

### 내부통근은 교통비 0, 시간가치는 계산 — 코드 수정 없음

거주지와 근무지가 같은 조합은 `fare` 가 NULL 이다
(`fare_method='내부통근_요금미산출'`). 같은 동 안 이동이라 Tmap 대중교통 경로를
뽑지 않았다. 네이버지도도 가까운 거리는 대중교통 경로를 주지 않는다.
실제로 걸어가는 경우가 많으므로 **교통비 0 은 타당하다.**

다만 시간가치까지 0 이 되면 내부통근 동이 구조적으로 가장 유리한 후보가 되어
5·6페이지 추천이 왜곡된다. 걸어가도 시간은 든다.

확인 결과 `_monthly` 가 `commute_min` 과 `oneway_fare` 를 애초에 분리해 다뤄
**이미 그렇게 동작하고 있었다.**

    commute_min 13.72   oneway_fare None
    fare None           time_value 99,072

코드 수정 없이 회귀 테스트만 넣었다(`tests/db/test_internal_commute.py`).
나중에 "교통비가 없으니 통근 부담도 없다"고 정리하다 시간가치까지 지우면
거기서 잡힌다.

## 판단 기록

### C5(소스에서 산식 복붙 자체를 금지) 배제

계획 시점의 전제는 "산식이 파이썬 세 군데에 복붙돼 있다"였다.
실제 구조를 확인한 결과 여러 벌인 것은 **의도된 분리**였다.

| 위치 | 기준 | 용도 |
|---|---|---|
| `web/service.py` | 사용자 입력 | 개인화된 화면 값 |
| `src/db/query_dong.py` | 21일·청년 상한 고정 | 427개 동을 같은 잣대로 비교 |
| DB 뷰 `v_dong_burden` | 조회 시점 계산 | 군집·SQL 분석·발표 수치 |

`build_page5` 주석이 이를 명시한다 — "조회 계층이 돌려준 fare·time_value 는
기본 가정으로 계산된 값이라 그대로 쓰면 3·4페이지와 어긋난다. 여기서 다시 만든다."

C5 는 "계산이 한 곳에만 있어야 한다"를 강제하므로 이 분리와 충돌한다.
원래 노리던 위험(파라미터가 갈리는 것)은 `test_param_sync.py` 가 덮고,
인자 누락은 `test_every_call_passes_region` 이 덮는다.

**따라서 C1~C4 만 도입하고 C5 는 배제한다.**

### 시간가치를 인자로 빼지 않음

`_monthly` 이 `TIME_VALUE_PER_HOUR` 를 모듈 상수로 읽는 것은 허용했다.

인자로 받아야 하는 것은 **호출 맥락마다 달라지는 값**뿐이다(`days`, `cap`).
확정 파라미터까지 인자화하면 호출부 4곳에 "빼먹을 수 있는 자리"가 새로 생기는데,
그게 애초에 사고의 원인이었다.

대신 그 상수가 `src/db/query_dong.py` 와 DB `dim_time_value` 에도 있으므로
값이 어긋나는지를 `test_param_sync.py` 가 감시한다.

### 안 터지는 지적은 실패로 만들지 않음

pyflakes 결과 중 `undefined name` 계열만 실패로 본다.
미사용 import, f-string 누락 등은 참고 출력으로만 남긴다.
크래시가 안 나는 것으로 계속 빨간불이면 테스트가 잔소리가 되고,
정작 중요한 실패까지 무시하게 된다.

## 알아둘 것

### 반복해서 나온 패턴

7건 중 4건이 같은 모양이었다 — **짝이 되는 두 자리의 방어 수준이 한 줄 다르다.**

| | 제대로 된 쪽 | 빠진 쪽 |
|---|---|---|
| None 방어 | `t_from` 의 `or 0` | `extra` 의 `.get(키, 0)` |
| 권역 전달 | 호출부 4곳 | `_support_rank` |
| 긴 키 우선 | `_LINE_COLOR` | `_MODE_KO` |
| 자기 제외 | `list_work_options` | `nearest_routed_work` |

한 곳을 고칠 때 같은 일을 하는 다른 곳을 함께 보지 않아서 생긴다.
값 비교로는 안 잡히므로 소스 검사(AST)와 짝 함수 동시 검사로 막는다.

### 모르는 것을 아는 것처럼 보여주지 않는다

이 프로젝트는 그 원칙을 여러 곳에서 지키고 있다.

- `no_data` 동에 "주거비를 산출하지 못했어요"라고 밝히고 인근 동을 대신 보여준다
- `_judge_policy` 가 모르는 값을 통과로 처리하지 않고 `unchecked` 로 남긴다
- `nearest_routed_work` 가 `requested_name` 을 함께 돌려줘 무엇을 대체했는지 밝힌다
- 승하차역 이름이 없으므로 지어내지 않고 수단·노선만 보여준다

2026-09-07 에 소득 미확인 배지를 추가해 마지막 구멍을 메웠다.

### 테스트가 못 잡는 것

값의 어긋남은 잡지만 **이름의 어긋남은 못 잡는다.**
`dim_time_value` 의 "2025년 최저임금" 오기가 그 예다. `10320 == 10320` 은 통과한다.
라벨·주석·근거 문구는 사람이 봐야 한다.

다만 문구 안에 숫자가 들어 있으면 잡을 수 있다.

같은지 검사한다(`test_note_number_matches_cap`).

### 알려진 폴백 목록

호출부가 인자를 빼먹었을 때 조용히 쓰이는 기본값. 목록을 테스트로 고정해 뒀다.

- `_diagnosis_cards(work_days=21)` · `recommend_dongs(work_days=21)`
- `build_page5(base_code='11650540', work_code='11680640')` — app.py 가 코드를
  안 넘기므로 항상 쓰인다. place 해석이 실패하면 엉뚱한 동 값이 정상처럼 표시될 수 있다.
- `_pass_for_age(None)` → 청년 기준
- `_deposit_monthly(deposit)` → 전체 중앙값 5.9%
- `list_work_options` · `list_home_options` · `nearest_routed_work` ·
  `policy_coverage` → `except Exception` 시 빈 결과
- `_judge_policy` 의 `unchecked` — 모르는 값을 통과로 처리하지 않는다(올바른 설계)
