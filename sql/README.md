# sql/ — 스키마 정의와 분석 쿼리

## 왜 필요했나

파이프라인이 끝나면 산출물은 CSV로 남는다. 분석을 한 번 돌리고 결과를 보는 데는 이걸로 충분하다. 그런데 서비스가 붙는 순간 성격이 달라진다.

사용자가 "보증금 1천만 원 이하"라고 조건을 걸면, 그 조건에 맞는 거래만 골라 행정동별 대표값을 다시 내야 한다. 57만 행 CSV를 매 요청마다 전체 스캔하면 사용자가 기다린다. 주거비·통근·유형·정책을 한 번에 붙이는 결합도 CSV 네 개를 각각 읽어 merge 하는 것보다 JOIN 한 번이 훨씬 낫다.

그리고 이 프로젝트에는 목적이 하나 더 있다. **적재 자체는 반나절이면 끝나고, 남는 것은 쿼리다.** 순위를 비교하고 그룹 안에서 다시 순위를 매기는 일을 윈도우 함수로 풀어본 기록이 이 폴더에 있다.

## 설계 원칙

### ① 가정은 컬럼이 아니라 테이블에 둔다

`monthly_time_cost`, `total_burden` 같은 컬럼을 일부러 만들지 않았다. 시간가치를 10,320원으로 박아 저장하면 "청년 평균임금 기준으로도 보자"는 말 한마디에 적재를 다시 해야 한다.

대신 `dim_time_value`에 시간가치를 행으로 두고, 뷰에서 `CROSS JOIN` 한다. 420행 × 시나리오 수가 자동으로 나오고, 기준을 바꾸는 민감도 분석이 `WHERE time_value_code = ...` 한 줄이 된다. 소득 시나리오 5단계, 생활비 환산 가정도 같은 방식이다.

### ② 행정동코드는 CHAR(8)이다

숫자가 아니라 식별자다. INT로 받으면 선행 0이 날아가고 결합키가 조용히 깨진다. 이름 결합은 스키마 차원에서 막았다 — 전처리에서 "창신제1동" vs "창신1동" 같은 표기 차이를 181건 겪었기 때문이다.

### ③ 집계값과 원자료를 둘 다 적재한다

`fact_dong_burden`(420행)에 이미 동별 표면주거비가 있는데 `fact_rent_transaction`(57만 행)도 넣는 이유는, **평균값에서 조건부 평균을 역산할 수 없기** 때문이다. 반 평균 70점을 알아도 남학생만의 평균은 원점수가 있어야 구한다. 사용자 예산 조건을 반영한 대표값은 거래 단위 원자료가 있어야 나온다.

### 01_schema.sql

테이블 12개와 뷰 2개를 만든다. 실행해도 데이터는 0행이다.

| 구분 | 테이블 | 행수 |
|---|---|---|
| 기준 | `dim_region` | 427 |
| | `map_region_legacy` | 9 |
| 파라미터 | `dim_time_value` / `dim_income_scenario` / `dim_living_cost_assumption` | 1 / 5 / 1 |
| 업무지구 | `dim_business_district` / `bridge_district_dong` | 9 / 40 |
| 분석 결과 | `fact_dong_burden` | 420 |
| | `fact_dong_type` / `fact_dong_type_features` | 427 / 427 |
| 원자료 | `fact_commute_od` | 164,032 |
| | `fact_commute_route` | 30,636 |
| | `fact_rent_transaction` | 577,745 |
| 정책 | `dim_policy` | (미확정) |

뷰 두 개가 반복 계산을 흡수한다.

- `v_dong_burden` — 시간가치 시나리오별 통합부담. 파라미터 테이블과 `CROSS JOIN`
- `v_district_commute` — 업무지구 × 거주동 대표 통근값. 지구 구성동을 유입량 가중평균하고, `route_coverage`로 경로 확보율을 같이 낸다

### 01b_seed_params.sql

시간가치·소득 시나리오·생활비 가정은 CSV 소스가 없어 여기서 직접 넣는다. 값을 바꾸려면 이 파일만 고쳐 다시 실행한다.

`dim_living_cost_assumption`은 **미확정 항목**이다. 생활소비부담지수가 강건 z-score라 금액이 아니고, 지수를 금액으로 환산하는 근거가 아직 없다. 자리표시용 값이라 이걸 쓰는 Q4 결과는 시산으로만 봐야 한다.

### 02_qc.sql

적재가 끝났는지가 아니라 **제대로 됐는지**를 본다. 판정 컬럼만 보면 된다.

| QC | 확인 내용 | 정상 |
|---|---|---|
| QC1 | 테이블별 행수 | 전부 OK |
| QC2 | 기준표 미등재 코드 | 0행 |
| QC3 | 업무지구 가중치 합 = 1 | 0행 |
| QC4 | 80%컷 경로 커버리지 + 지구별 확보율 | 100% |
| QC5 | 파이썬 순위 vs SQL `RANK()` | 불일치 0~5 |
| QC6 | 유형 분포 + 데이터부족 동 + 표면주거비 집계 대조 | 6유형 + 7개 |
| QC7 | 한글·금액 단위 육안 확인 | — |

**QC6에 표면주거비 집계 대조를 넣었다.** 파이프라인이 계산한 `fact_dong_burden.surface_housing_cost`와 유형화 입력값(`fact_dong_type_features`)을 비교한다. 두 트랙이 같은 원자료 위에 서 있는지 확인하는 장치이며, 실측 결과 420개 동 전부 차이 0이었다.

**QC5도 이 파일의 핵심이다.** `fact_dong_burden`에 파이썬이 계산한 순위를 `rank_burden_src`로 같이 저장해두고, SQL 윈도우 함수 결과와 대조한다. 적재 과정에서 값이 뒤틀리지 않았음을 자동으로 증명한다.

실측 결과 불일치 10개가 나왔고 차이는 전부 ±1이었다. 표면주거비를 INT로 선언해 소수점이 잘린 탓이며, 값이 촘촘한 구간에서만 순위가 엇갈린다. 산식은 동일하다.

### 02_analysis_queries.sql

| 쿼리 | 내용 | 기법 |
|---|---|---|
| Q1 | 월세착시·숨은효율 순위 괴리 | CTE + `RANK() OVER` |
| Q2 | 업무지구별 추천 주거지 상위 10 | 다중 CTE + `NTILE` + `ROW_NUMBER() PARTITION BY` |
| Q3 | 지구 간 추천 중복률 매트릭스 | CTE self-join |
| Q4 | 소득 시나리오별 저축 여력 | `CROSS JOIN` 파라미터 격자 |
| Q5 | 6개 유형 프로파일 | `GROUP BY` + 조건부 집계 |
| Q6 | 정책·금융상품 조건 매칭 | NULL=무제한 규칙 조건 조인 |

## 대표 결과

Q2·Q3에서 **"강남 근무자와 여의도 근무자의 추천 상위 10곳 중 공통은 2곳(20%)뿐"**이 나왔다. Q7은 여기서 한 걸음 더 나가 **주거비 10만원을 아낄 때 통근으로 되돌아가는 비율이 근무지에 따라 3~31%로 갈린다**는 것을 보였다.

수치와 해석은 [`docs/SQL_분석결과.md`](../docs/SQL_분석결과.md)에 있다.

## 읽을 때 주의할 것

**부담유형은 정의가 두 개다.** Q1의 `CASE WHEN rank_gap <= -50`은 이 쿼리에서만 쓰는 임시 구간이라 B가 20개 이상 나온다. 확정 부담유형(A 197 / B 13 / C 13 / D 197)은 `build_total_burden.py`가 계산해 `fact_dong_burden.burden_type_src`에 들어 있다. 화면·발표에는 그쪽을 쓴다.

**유형은 6개이고 7개 동은 유형이 없다.** `fact_dong_type`은 427행 전체를 담되 데이터가 없는 7개 동은 `type_name`이 NULL이고 `flag_insufficient=1`이다. 빼버리면 서비스에서 "데이터 부족"인지 "코드 오류"인지 구분할 수 없다. 추천 후보에서는 제외한다.

**`flag_boundary`가 붙은 63개 동은 유형을 단정하지 않는다.** FuzzyCMeans 소속도가 낮아 두 유형 성격을 함께 갖는 동이다. 화면에서는 유형명보다 실제 수치를 앞세우는 편이 낫다.

**업무지구별 거주동 수가 다르다.** 도심·강남·여의도는 427개 전부에서 경로가 있지만 마곡·강서는 274개뿐이다. 80% 컷 기반이라 "그 지구로 출근하는 사람이 적은 동"이 빠진 것인데, 결과를 쓸 때 "마곡 근무자 추천 후보는 274개 동 중에서 뽑힌 것"이라고 밝혀야 한다.

**Q4는 아직 발표에 쓸 수 없다.** 생활비 환산 가정이 자리표시용이라 350만 원 시나리오에서 415개 동 전부가 저축률 20%를 달성한다고 나온다. 변별력이 없다.
