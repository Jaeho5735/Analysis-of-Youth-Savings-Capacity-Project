# 지표 산출 파이프라인 (src/indicators/) — 4개 파일이 하는 일

## 큰 그림 먼저

이 4개 파일은 두 가지 목표를 위해 순서대로 실행된다.

> **① 청년 1인가구 실거래가 데이터에 외부 공식 통계(한국부동산원 전월세전환율)를 붙여서 행정동별 표면 주거비를 산출하고, ② 서울시 상권분석서비스 데이터로 행정동별 생활소비부담지수를 산출한 뒤, 이 둘을 하나로 결합하는 것**

표면 주거비 산식은 처음부터 정해져 있었다.

```
표면 주거비 = 실제 월세 + (실제 보증금 × 전월세전환율 ÷ 12)
```

문제는 `전월세전환율`이 우리 데이터 어디에도 없는 **외부 지표**라는 점이었다. 이걸 구해서 붙이는 과정이 ①②③, 그리고 생활소비부담지수를 산출해 결합하는 과정이 ④다.

```
① load_conversion_rate.py       (단독다가구·연립다세대 전환율 정리)
        ↓
② load_officetel_rate.py        (오피스텔 전환율 정리, 별도 파일인 이유는 구조가 다르기 때문)
        ↓
③ calc_surface_housing_cost.py  (실거래가 데이터에 전환율을 붙여 표면 주거비 계산 + 행정동별 집계)
        ↓
④ calc_consumption_burden_index.py  (생활소비부담지수 산출 + 표면 주거비와 결합)
```

이 폴더는 **지표를 만드는 일**만 한다. 만든 지표가 맞는지 따지는 코드는 `src/validation/`에, 지표를 합쳐 답을 만드는 코드는 `src/analysis/`에 있다. 실행 주기가 다르고 입력도 다르기 때문에 섞지 않았다.

- **검증** (`src/validation/`) — 타당성 검증 2종, 기반 변수 변형 비교. 지표 산식이나 기준을 바꿀 때 돌린다
- **분석** (`src/analysis/`) — 업무지구 정의, 통합부담 산출, 행정동 유형화. 지표가 다 나온 뒤에만 돌 수 있다

이 폴더를 만드는 과정에서 겪은 버그와 수정 이력은 분량이 커서 [`docs/디버깅_이력_지표산출.md`](../../docs/디버깅_이력_지표산출.md)로 분리했다. 같은 종류의 문제를 다시 만났을 때 그쪽을 먼저 보면 된다.

## ① load_conversion_rate.py — 단독다가구·연립다세대 전환율 정리

**왜 필요했나**: 표면 주거비 산식에 넣을 전월세전환율을 어디서 구할지부터 막혔다. 처음엔 "구별로 다르게 할지, 서울 전체 단일값으로 할지"를 고민했는데, 알아본 결과 이 결정 자체가 무의미했다 — 서울시가 발표하던 자치구별·주택유형별 통계(서울 열린데이터광장)는 **2022년에 서비스가 종료**됐고, 한국부동산원의 예전 권역별 통계도 **2018년 1분기로 수록이 끝나** 있었다. 즉 "얼마나 세밀하게 쓸지"보다 먼저 "지금도 갱신되는 통계가 있는지"부터 찾아야 했다.

**최종적으로 찾은 데이터**: 한국부동산원 R-ONE의 "지역별 전월세 전환율" — 단독주택/연립다세대/아파트/종합주택 4종류로 나뉘어 있고, **서울시 5개 권역(도심권/동남권/동북권/서남권/서북권) 단위로 월별 최신 데이터**까지 살아있었다. 자치구 단위는 아니지만, 서울 전체 단일값보다는 훨씬 정밀하다.

**문제였던 점**: 다운받은 표에 "강북지역"/"강남지역"이라는 항목이 섞여 있었는데, 이건 실제 권역이 아니라 **다른 권역들을 합친 요약값**이었다(강북지역 = 도심권+동북권+서북권, 강남지역 = 동남권+서남권). 그대로 뒀으면 나중에 집계할 때 같은 자치구 데이터가 이중으로 잡힐 뻔했다.

**하는 일**: 단독주택/연립다세대 CSV 두 개에서 강북·강남 요약행을 빼고 실제 5개 권역만 남긴 뒤, 가로형(월별 컬럼)을 세로형(연월 하나의 컬럼)으로 바꾼다. 그리고 "자치구 → 권역" 매핑표도 별도로 만들어둔다 — 우리 실거래가 데이터는 자치구 단위인데 전환율은 권역 단위라서, 나중에 이 둘을 이어줄 다리가 필요하기 때문이다.

**입력 → 출력**: `지역별_전월세_전환율_단독주택.csv`, `지역별_전월세_전환율_연립_다세대.csv` → `전월세전환율_권역별.csv`, `자치구_권역_매핑.csv`

## ② load_officetel_rate.py — 오피스텔 전환율 정리 (별도 파일인 이유)

**왜 따로 만들었나**: 오피스텔은 애초에 다른 통계(오피스텔 가격동향조사)에서 나온다. 처음엔 "오피스텔은 시군구 선택이 안 되는 조사라 서울 전체 단일값만 쓸 수 있겠다"고 판단했는데, 실제로 받아보니 예상보다 훨씬 정밀했다 — **권역별로도 나뉘어 있고, 거기에 더해 면적구간(40㎡이하 / 40㎡초과~60㎡이하)까지 세분화**되어 있었다. 구조 자체가 단독주택·연립다세대 표와 다르기 때문에(권역만 있는 게 아니라 면적구간이라는 축이 하나 더 있음), 같은 로더로 처리할 수 없어서 별도 파일로 분리했다.

**하는 일**: 오피스텔 CSV에서 서울 5개 권역 × 2개 면적구간(전체 60㎡ 이하 데이터만 다루므로 이 두 구간이면 충분) 조합만 남기고, 마찬가지로 세로형으로 변환한다.

**입력 → 출력**: `(월)_오피스텔_전월세전환율_2024년1월~.csv` → `전월세전환율_오피스텔_권역별.csv`

## ③ calc_surface_housing_cost.py — 실제 계산 + 행정동별 집계

**왜 ①②와 분리했나**: ①②는 "외부 통계 정리"고, ③은 "우리 데이터에 그걸 적용해서 계산"하는 완전히 다른 작업이다. 원본 CSV 파싱 로직과 계산 로직을 분리해두면, 나중에 산식이 바뀌거나 필터링 기준이 바뀔 때 ③만 다시 돌리면 되고, 전환율 원본을 매번 다시 파싱할 필요가 없다.

**하는 일**:
1. 청년 1인가구 실거래가 데이터의 `시군구명`(자치구)을 매핑표로 **권역**으로 변환
2. 단독다가구·연립다세대는 (주택유형, 권역, 연월) 기준으로, 오피스텔은 (권역, 면적구간, 연월) 기준으로 전환율을 붙인다
3. 전환율 데이터가 없는 연월(수집 기간 밖)은 가장 가까운 달의 값으로 대체하고 `전환율_범위외_보정` 컬럼에 표시. 가까운 달 판정은 YYYYMM을 그냥 정수로 빼면 12월↔1월 경계에서 틀어지므로(202312와 202401의 실제 거리는 1개월인데 정수로는 89), 연×12+월로 바꾼 값으로 계산한다
4. 거래 1건 단위로 표면 주거비를 계산한 뒤, 행정동 × 주택유형별로 **중앙값**을 집계
5. 추가로 행정동당 1행짜리 pooled 집계(`표면주거비_행정동_통합.csv`)도 만든다 — 유형별 중앙값을 나중에 평균내면 표본 20건짜리 유형과 500건짜리 유형이 동일한 발언권을 갖게 되어 왜곡되므로, 개별 거래에서 직접 중앙값을 내야 한다. K-Means 등 군집화에는 이 pooled 버전을 쓴다

**QA 과정에서 발견하고 고친 문제 1 (필터링 기준 문제)**: 계산 결과의 최솟값이 비정상적으로 낮게 나와서(1.475만원) 확인해보니, `filter_youth_household.py`에 월세=0인 행이나 "월세 1만원 + 보증금 100만원"처럼 **자릿수가 빠진 것으로 보이는 입력 오류 행**이 걸러지지 않고 남아있었다. 월세 상한을 임의의 숫자 대신 분포의 상위 1%로 객관적으로 정했던 것과 같은 논리를, 하한에도 대칭으로 적용해서 해결했다 (하위 1% = 10만원을 컷오프로 사용).

**QA 과정에서 발견하고 고친 문제 2 (행정동명 캐시 오염)**: `표면주거비_행정동별.csv`의 `행정동명_최종` 값 일부가 "서울특별시 강남구 개포2동"처럼 시/구가 붙은 채로 섞여 있었다. 표면 주거비 계산 단계가 아니라 그 이전 법정동→행정동 매칭 단계(`resolve_precise_jibun.py`)의 캐시 오염 문제였다. 자세한 원인과 전체 해결 과정은 아래 "디버깅 기록" 섹션 참고.

**QA 과정에서 발견하고 고친 문제 3 (동명이인 행정동)**: 서울 안에 이름이 완전히 같은 행정동(신사동: 강남구/관악구/은평구)이 있어, 이름만으로 집계하면 서로 다른 동네가 섞이는 문제가 뒤늦게 발견됐다. `행정동코드_최종`을 기준으로 집계하도록 수정 — 자세한 내용은 "디버깅 기록 — 코드 리뷰 반영" 섹션 참고.

**결측 확인 — 서울 427개 행정동 중 7개가 산출물에 없는 이유**: `행정동_기준코드표.csv`(427개) 대비 `표면주거비_행정동_통합.csv`는 420행이다. 빠진 7개는 하계2동·상계8동·상계9동(노원구), 반포본동·반포2동(서초구), 오륜동·잠실7동(송파구)이다.

원인은 결측이 아니라 필터 결과다. `filter_youth_household.py`가 청년 1인가구 추정 대상을 단독·다가구, 연립·다세대, 오피스텔로 한정하고 **아파트는 애초에 제외**한다(기획안 2-4절 — 아파트는 면적·보증금이 커서 소형 임차시장 추정 목적과 안 맞음). 이 7개 동은 주택 재고가 사실상 아파트 단지 위주라, 필터를 통과하는 거래 자체가 존재하지 않는다. 국토부 원본에서 이 7개 동을 조회하면 아파트 거래는 있어도 단독·연립·오피스텔 거래가 0건이거나 극소수임을 확인할 수 있다.

삭제가 아니라 **결측으로 처리**한다 — `행정동_기준코드표.csv`와 `check_region_coverage.py` 진단 결과에 `in_표면주거비 = False`로 표시되며, 지도·서비스 화면에서는 이 7개 동을 "표본 없음"으로 별도 표시해야 한다(아파트 거주 청년은 본 분석의 추정 범위 밖이라는 한계와 동일한 맥락).

**입력 → 출력**: `전월세_실거래가_청년1인가구.csv` + `전월세전환율_권역별.csv` + `전월세전환율_오피스텔_권역별.csv` + `자치구_권역_매핑.csv` → `표면주거비_거래단위.csv`(QA용), `표면주거비_행정동별.csv`(유형별), `표면주거비_행정동_통합.csv`(pooled, 군집화용, 420행)

**결과**: 577,761 / 577,761행(100%) 계산 성공. 행정동 커버리지는 427개 중 420개(위 참고).

## ④ calc_consumption_burden_index.py — 생활소비부담지수 산출 + 결합

**왜 필요했나**: 표면 주거비만으로는 "그 동네에 살 때 매달 나가는 밥값·생필품비" 같은 생활물가 체감도를 반영하지 못한다. 청년이 특정 행정동에 살 때 숨만 쉬어도 나가는 외식비·마트 비용 등 "동네 장바구니 물가"를 정량화한 보조 지표가 필요했다.

**산식 원칙**: 기반 변수는 총매출액이 아니라 **건당 결제금액**이다. 총매출액은 상권 규모·점포 수·유동인구에 좌우되므로 그 지역의 소비 가격 수준을 대표하지 못한다(총매출이 높은 동네는 "비싼 동네"가 아니라 "장사가 잘 되는 동네"일 수 있다). 그리고 최초 기획안의 산식(모든 업종을 섞어서 평균)에도 오류가 있었다 — 업종을 안 나누고 평균을 내면 거래건수가 많은 업종(편의점 등)이 결과를 지배해버린다. 그래서 **업종별로 먼저 z-score를 계산한 뒤, 행정동별로 그 z-score들을 평균**내는 순서로 수정했다.

**하는 일**:
1. 서울시 상권분석서비스 추정매출 데이터(2023~2026년 4개 파일, 분기별)를 통합. 파일마다 수집 기간이 롤링되어(예: "2026년" 파일에 2025년 분기까지 포함) 겹치는 경우가 있어 (분기, 행정동_코드, 업종) 기준으로 중복 제거
2. 청년 생활밀접 업종 10개(한식·중식·일식·제과·분식·치킨·패스트푸드·커피-음료·슈퍼마켓·편의점)만 필터링
3. 매출건수 하위 5%(표본이 너무 적어 단가가 왜곡된 행)를 분위수 기준으로 제거한 뒤, (행정동, 업종)별로 **매출금액 합계 ÷ 매출건수 합계**로 건당 결제금액을 산출. 행별 비율을 먼저 내고 평균내면 거래 50건짜리 분기와 1만 건짜리 분기가 같은 발언권을 갖게 되므로 반드시 합산한 뒤 나눈다 (프로젝트 원칙 "집계값끼리 계산하지 않는다"의 적용)
4. 업종별로 median/MAD 기반 강건 z-score를 계산한 뒤 ±3으로 클리핑 → 행정동별 평균 → 생활소비부담지수 확정
5. 표면 주거비(pooled 버전)와 (시군구명, 행정동명) 기준으로 결합, `validate="many_to_one"`으로 결합 키 중복 시 즉시 에러가 나도록 방어

행정동 집계·결합 키는 `행정동_코드`가 아니라 `(시군구명, 행정동_코드_명)`이다. 이유와 배경은 아래 "디버깅 기록 — 코드 리뷰 반영" 섹션 참고. 행정동명 정규화 로직(`normalize_dong_name`)은 `resolve_precise_jibun.py`와 함께 쓰기 위해 `src/utils/dong_names.py`로 분리했다.

**QA 과정에서 발견하고 고친 문제**: 결합 시 매칭 실패가 반복적으로 발생했다. 원인은 행정동명 표기 불일치였고, 이 문제를 추적·해결한 전체 과정은 아래 "디버깅 기록" 섹션에 시간 순서대로 정리했다.

**입력 → 출력**: `서울시_상권분석서비스_추정매출-행정동_*.csv`(4개) + `표면주거비_행정동_통합.csv` + `행정동_공식명_목록.csv` → `생활소비부담지수_행정동별.csv`, `표면주거비_생활소비부담지수_결합.csv`(최종 결합본)

**결과**: 지수 산출 행정동 425개, 표면 주거비와 결합 시 420행 중 매칭 실패 5행(신설동·용두동·개포3동·상일제1·2동 — 전부 원인 규명된 구조적 한계이며, 각각의 신 명칭이 용신동·일원2동·상일동임을 확인해 코드 매핑표로 연결할 수 있는 상태).

## 한 줄 요약표

| 순서 | 파일 | 한 줄 요약 |
|---|---|---|
| ① | load_conversion_rate.py | 단독다가구·연립다세대 전환율을 권역별로 정리한다 |
| ② | load_officetel_rate.py | 오피스텔 전환율을 권역×면적구간별로 정리한다 (구조가 달라 별도 파일) |
| ③ | calc_surface_housing_cost.py | 실거래가에 전환율을 붙여 표면 주거비를 계산하고 행정동별로 집계한다 |
| ④ | calc_consumption_burden_index.py | 생활소비부담지수를 산출하고 표면 주거비와 결합한다 |

데이터가 갱신되면 ①~④를 순서대로 다시 돌린다. 산식이나 기준을 바꿨다면 `src/validation/`의 검증도 함께 돌려야 한다. 보고서에 적힌 수치가 현재 산출물과 어긋나면 그때부터 문서를 믿을 수 없다.

## 최종 산출물

- `표면주거비_행정동별.csv` — 행정동 × 주택유형별 표면 주거비 중앙값, 표본수, 표본부족 여부 (577,761/577,761행, 100%)
- `표면주거비_행정동_통합.csv` — 행정동당 1행, pooled 중앙값. **군집화(K-Means 등)에는 이 파일을 사용**
- `생활소비부담지수_행정동별.csv` — 행정동별 생활소비부담지수 425행 (건당 결제금액 기반, median/MAD 강건 z-score + 클리핑, 최근1년 비교값·반영업종수·업종부족 플래그 포함)
- `표면주거비_생활소비부담지수_결합.csv` — 두 지표를 결합한 최종 파일 (420행 중 매칭 실패 5행)
- `행정동_공식명_목록.csv` — 서울 행정동 공식 명칭·코드 참조 목록 (`dong_matcher.py` 산출. 현재는 `src/reference/`의 기준 코드표와 역할이 겹쳐 정리 대상)

검증 산출물(`지수검증_행정동별.csv`, `생활소비부담지수_변형비교.csv`)은 `src/validation/` 문서를 참고한다.


## 알아둘 것

**매칭 실패 5행은 버그가 아니다.** 두 지표를 결합할 때 남는 5개 동(신설동·용두동·개포3동·상일제1·2동)은 표기 문제가 아니라 실제 행정동 개편 때문이다. `src/reference/`의 폐지코드 매핑으로 해결한다.

**행정동 개수가 소스마다 다르다.** 표면주거비 420 / 지수 425 / 공식 427. 어느 기준인지 항상 밝혀야 한다.
