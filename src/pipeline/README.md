# src/pipeline/ — 산출물을 다시 만드는 단계

## 왜 필요했나

`reference → preprocessing → indicators → analysis` 는 **처음부터 끝까지 다시
도는** 파이프라인이다. 원본 CSV를 읽어 지표를 만들고 산출물을 떨어뜨린다.

그런데 실제로는 전부 다시 돌릴 수 없는 상황이 계속 생겼다.

- Tmap 경로 30,839건 재조회는 API 호출 제한 때문에 며칠이 걸린다
- 파라미터 하나(정기권 상한, 시간가치)만 바꿔 다시 계산하고 싶다
- 팀원이 새로 준 파일 하나만 갈아끼우고 나머지는 그대로 두고 싶다

이 폴더는 그 요구를 담당한다. **이미 있는 산출물을 입력으로 받아, 바뀐 부분만
다시 만든다.** 전체 재실행이 아니라 부분 갱신이다.

원래 이 스크립트들은 프로젝트 루트에 흩어져 있었다. 루트에 파이썬 파일이 널려
있으면 어디부터 읽어야 할지 알 수 없어 여기로 모았다.

## 문제였던 점

### ① 산출물을 덮어쓰면 되돌릴 수 없다

부분 갱신은 정의상 **기존 파일을 갈아엎는 일**이다. 잘못된 파라미터로 한 번
돌리면 몇 시간짜리 결과가 사라진다.

그래서 이 폴더의 스크립트는 덮어쓰기 전에 원본을
`<이름>_<타임스탬프>.bak.csv` 로 백업한다. 백업본은 `.gitignore` 대상이라
저장소에는 올라가지 않는다.

### ② 경로를 코드에 박으면 재사용이 안 된다

"이 파일을 저 파일로 갈아끼운다"가 목적이라 입출력이 매번 다르다. 상수로
박아두면 파일이 바뀔 때마다 코드를 고치게 된다.

**그래서 경로를 전부 커맨드라인 인자로 받는다.** 다만 기본값을 함께 두어,
평소에는 인자 없이 그냥 실행하면 표준 경로로 돈다. 파일을 갈아끼울 때만
해당 인자를 준다.

이 스크립트들이 폴더를 옮겨도 동작하는 이유이기도 하다.
`PROJECT_ROOT` 같은 위치 의존 상수가 없다.

### ③ 부분 갱신은 조용히 틀리기 쉽다

전체 재실행은 중간에 죽으면 알 수 있다. 부분 갱신은 **행 수가 맞으면 성공한
것처럼 보인다.** 실제로는 결합키가 어긋나 절반이 NaN이어도 파일은 생긴다.

그래서 각 스크립트는 실행 전에 입력 파일 존재를 확인하고, 실행 후 행 수와
결측 건수를 로그에 남긴다. 기준표에 없는 코드는 버리지 않고 격리 CSV로
떨어뜨린다(프로젝트 전체 원칙: 제외 대신 플래그).

**네 스크립트 모두 `--dry-run` 을 지원한다.** 아무것도 쓰지 않고 무엇을 할지와
결과가 어떻게 바뀌는지만 출력한다. 덮어쓰기 전에 이걸 먼저 보는 것이 기본이다.
Tmap 재조회는 특히 그렇다 — 호출이 곧 시간이자 비용이라, 준비 상태 점검과
실제 호출을 분리해두었다.

## 하는 일

```
requery_commute_routes.py   Tmap 경로 재조회 (실패분·누락분만)
        ↓
reselect_routes.py          여러 후보 경로 중 대표 경로 재선택
        ↓
rebuild_analysis_ready.py   경로 원본 → 분석용 경량 CSV 재생성
        ↓
rebuild_commute_burden.py   통근부담 지표 재산출
```

위에서 아래로 의존한다. 경로를 다시 부르면 대표 경로를 다시 고르고, 그러면
분석용 파일과 통근부담을 차례로 다시 만들어야 한다. **중간부터 시작해도
된다** — 앞 단계 산출물이 이미 있으면 그것을 입력으로 쓴다.

### requery_commute_routes.py

Tmap 대중교통 API로 거주동 × 근무동 경로를 다시 부른다.

전체를 다시 부르지 않는다. `data/requery_failures.csv` 에 남은 실패 조합과,
OD에는 있는데 경로 파일에 없는 조합만 대상으로 한다. API 호출량이 그대로
시간과 비용이라 재조회 범위를 좁히는 것이 핵심이다.

```
python src/pipeline/requery_commute_routes.py --dry-run   # 호출 없이 점검
python src/pipeline/requery_commute_routes.py --limit 50  # 50건만 시험
python src/pipeline/requery_commute_routes.py             # 전체 실행
```

| 인자 | 기본값 | 내용 |
|---|---|---|
| `--od` | OD 선별 CSV | 재조회 대상 조합 |
| `--coord` | 행정동 좌표 CSV | 출발·도착 좌표 |
| `--out` | 재조회 결과 CSV | 저장 위치 |
| `--limit` | 0(제한 없음) | 시험용 건수 제한 |
| `--dry-run` | — | 호출 없이 준비 상태만 점검 |

`--limit` 가 따로 있는 이유는 API 호출이 곧 비용이기 때문이다. 전체를 돌리기
전에 소량으로 응답 형태를 먼저 확인한다.

**입력** OD 선별 파일, 행정동 좌표 파일
**출력** 재조회 결과 CSV, 실패 목록

### reselect_routes.py

한 조합에 후보 경로가 여러 개 나온다. 그중 무엇을 대표로 쓸지 다시 고른다.

기준을 바꿔가며 여러 번 돌린 이력이 있다. 최단시간만 보면 환승 3회짜리가
뽑히고, 환승 최소만 보면 한없이 오래 걸리는 경로가 뽑힌다. 지금은 소요시간과
환승을 함께 보되 도보 비중이 과도한 경로를 배제한다.

```
python src/pipeline/reselect_routes.py --dry-run
python src/pipeline/reselect_routes.py
```

| 인자 | 기본값 | 내용 |
|---|---|---|
| `--csv` | 재조회 결과 CSV | 경량 경로 파일 |
| `--jsonl` | 원본 응답 JSONL | 후보 경로 전체가 든 원본 |
| `--out` | 재선택 결과 CSV | 저장 위치 |

**입력을 두 개 받는 이유**가 이 스크립트의 핵심이다. 경량 CSV에는 이미 선택된
대표 경로 한 줄만 있어서, 다른 후보를 고르려면 원본 JSONL 로 돌아가야 한다.
원본을 버리지 않고 `.jsonl` 로 보관한 결정이 여기서 값을 한다.

**입력** 경량 경로 CSV + 원본 응답 JSONL
**출력** 조합당 1행 대표 경로, `docs/재선택_결과.csv` 진단표

### rebuild_analysis_ready.py

Tmap 원본 응답에서 분석에 쓰는 컬럼만 뽑아 경량 CSV를 만든다.

원본 JSON은 응답 하나가 100KB를 넘고 전수 30,839건이면 수 GB다. 분석에
필요한 것은 소요시간·거리·요금·환승·노선뿐이라, 원본은 `.jsonl` 로 따로 두고
경량본만 파이프라인에 태운다.

```
python src/pipeline/rebuild_analysis_ready.py --dry-run
python src/pipeline/rebuild_analysis_ready.py
```

| 인자 | 기본값 | 내용 |
|---|---|---|
| `--od` | OD 선별 CSV | 가중치·목적지 순위를 다시 붙일 원천 |
| `--old` | 기존 분석용 CSV | 갱신 대상. 실행 시 타임스탬프 백업 |
| `--new` | 재선택 결과 CSV | 갈아끼울 새 경로 |
| `--out` | 분석용 CSV | 저장 위치(보통 `--old` 와 같다) |

**`--old` 와 `--new` 를 함께 받는 이유**는 전체 교체가 아니라 부분 교체이기
때문이다. 재조회한 조합만 새 값으로 바꾸고 나머지는 기존 값을 그대로 둔다.
전체를 새로 만들면 재조회하지 않은 3만 건이 사라진다.

**입력** OD 선별 파일, 기존 분석용 CSV, 재선택 결과
**출력** `commute_routes_analysis_ready.csv`, 백업본, 격리 CSV

### rebuild_commute_burden.py

경로 파일이 바뀌면 통근부담 지표를 다시 계산해야 한다. 월 교통비, 월 통근시간,
대표 편도시간 같은 값이 전부 경로에서 나오기 때문이다.

```
python src/pipeline/rebuild_commute_burden.py --dry-run
python src/pipeline/rebuild_commute_burden.py
```

| 인자 | 기본값 | 내용 |
|---|---|---|
| `--routes` | 분석용 경로 CSV | 갱신된 경로 |
| `--metrics` | 네트워크 지표 결합본 | 통근권·엔트로피 등 군집 입력 |
| `--out` | 네트워크 지표 결합본 | 저장 위치 |

`--metrics` 는 12번 노트북이 만든 결합본이다. 통근권 코드와 목적지 엔트로피
같은 군집 입력 변수가 여기 들어 있어, **경로만 갈아끼우고 네트워크 지표는
보존해야 한다.** 통째로 다시 만들면 군집 입력이 사라져 유형화를 다시 돌려야
한다.

**입력** 분석용 경로 CSV, 네트워크 지표 결합본
**출력** 갱신된 통근부담 CSV, 백업본

## 다시 돌린 뒤 해야 할 것

통근부담이 바뀌면 그 아래가 전부 따라와야 한다.

```
rebuild_commute_burden.py
        ↓
src/analysis/build_total_burden.py     통합부담 재산출
        ↓
src/db/load_to_db.py                   MySQL 재적재
        ↓
sql/02_qc.sql, sql/05_qc_transport_pass.sql   검증
```

`build_total_burden.py` 는 `--dry-run` 으로 먼저 돌려 부담유형 A/B/C/D 분포가
얼마나 흔들리는지 보는 편이 안전하다. 서비스 추천 결과가 여기서 갈린다.

## 요약

| 파일 | 역할 | 실행 주기 |
|---|---|---|
| `requery_commute_routes.py` | Tmap 경로 재조회 | 실패·누락이 쌓였을 때 |
| `reselect_routes.py` | 대표 경로 재선택 | 선택 기준을 바꿀 때 |
| `rebuild_analysis_ready.py` | 분석용 경량 CSV 재생성 | 경로가 바뀌었을 때 |
| `rebuild_commute_burden.py` | 통근부담 지표 재산출 | 경로가 바뀌었을 때 |

일회성 진단 스크립트는 이 폴더가 아니라 `scripts/` 에 있다. 파이프라인의
일부인지(여기) 한 번 확인하고 마는 것인지(저기)로 나눈다.
