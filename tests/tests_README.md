# tests

`web/`·`src/` 의 계산이 어긋나지 않는지, 각 함수가 옳은 답을 내는지 검사한다.

## 왜 있나

2026-09-06 에 같은 총부담 계산이 세 군데에 따로 적혀 있어서 같은 조건에
3페이지 141.6만 / 5페이지 139.4만이 나왔다. 산식은 통합했지만
같은 종류의 사고가 다시 나지 않게 하는 장치가 필요해 2026-09-07 에 붙였다.

도입 과정에서 실제 버그 7건을 찾았다. 해석과 상세 기록은
`docs/pytest-results.md` 참고.

## 실행

```bash
pytest -m "not db"    # DB 없이. 2초. 개발 중에는 이것으로 충분하다
pytest                # 전체 249건. 45초. 커밋 전에 한 번
pytest -rP            # 참고용 출력까지 본다
```

`db` 마커가 붙은 것만 MySQL 이 필요하다.

## 규칙

- **검사는 계산에 묶고 화면에 묶지 않는다.** 각 페이지는 계산 결과를
  `data["_calc"]` 에 남긴다. 화면 문자열을 파싱하면 템플릿만 바꿔도 깨진다.
- **`_calc` 는 계산이 끝난 직후에 남긴다.** 페이지 함수는 조기 return 이 여럿이라
  함수 끝에 두면 일부 경로에서 값이 안 남는다.
- **일치만 보지 않는다.** 네 페이지가 똑같이 입력을 무시하면 값은 일치한다.
  입력을 바꿨을 때 전부 움직이는지(반응)를 함께 본다.
- **산식을 한 곳에 모아도 인자를 빼먹으면 같은 사고가 난다.**
  `_deposit_monthly` 처럼 여러 곳에서 부르는 헬퍼는 호출부 전수를 AST 로 검사한다.
- **같은 일을 하는 함수는 조건이 같아야 한다.** `list_work_options` 에만 있고
  `nearest_routed_work` 에는 없던 조건 한 줄이 "자기 동네로 출근"을 대체안으로
  만들었다. 짝이 되는 함수는 같은 케이스로 함께 검사한다.
- **모르는 것이 화면까지 전달되는지 본다.** 조회 계층이 `unchecked` 를 옳게
  남겨도 표시 계층이 버리면 결과는 같다. 계산만이 아니라 전달도 검사한다.
- **부분일치로 찾는 표는 긴 키가 먼저다.** `_MODE_KO`·`_LINE_COLOR` 처럼
  `key in text` 로 훑는 표는 순서 자체를 테스트한다.
- **`except Exception: return []` 인 함수는 "비어 있지 않은지"를 본다.**
  SQL 이 깨져도 빈 목록이 되어 화면은 정상처럼 보인다.
  정상적인 빈 결과와 고장 난 빈 결과를 구분하는 것이 요점이다.
- **빈 결과는 `== []` 로 비교하지 않는다.** pymysql 의 `fetchall()` 은 튜플을
  돌려준다. `not rows` 로 본다.
- **소스를 문자열로 훑지 않는다.** 주석에 적힌 검산 기록까지 걸린다. AST 를 쓴다.
- **안 터지는 지적은 실패로 만들지 않는다.** 미사용 import 같은 것까지 빨간불이면
  정작 중요한 실패를 무시하게 된다. 참고 출력으로만 남긴다.
- **고칠 수 없는 것도 기록한다.** 판단이 필요한 동작은 "현재 이렇다"를
  테스트로 남겨, 바뀌면 실패하면서 검토를 강제한다.
